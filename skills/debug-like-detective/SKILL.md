## 这是什么

一句话：像侦探破案一样调 bug——先复现，再假设，再验证，最后才动手。

最烂的调试方式："试试改这里看看"。改完好像好了，不知道为什么好；没好，再改别处。三个小时过去，代码里多了五处莫名其妙的改动，bug 还在，还引入了两个新 bug。

这个 skill 规定：复现不了的 bug，不许动手修。每次只改一个变量。修完必须说清楚根因，说不清楚等于没修完。

## 何时用

- 任何 bug：报错、行为不对、数据不对
- 测试挂了，找不到原因
- 线上异常、用户反馈的问题
- "在我机器上是好的"——这种最要按流程走

## 工作流

### 第一步：复现

先写出最小复现步骤，写下来：

- 运行什么命令 / 点哪里
- 输入是什么
- 环境是什么（系统、版本、配置）
- 期望发生什么，实际发生什么

复现不了的 bug，不许动手修。你在修一个你没见过的东西，修对了是运气，修错了是常态。

如果用户说"偶尔出现"，先想办法提高复现概率：加日志、多跑几次、构造极端输入。实在复现不了，先加上足够的日志和监控，等它下次出现，而不是对着空气改代码。

### 第二步：收集证据

动手之前，先收集：

1. 报错信息全文。不许只看第一行，stack trace 拉到最后看。
2. 相关日志。把报错时间点前后的日志都看一遍。
3. 最近改了什么：`git log`、`git diff`。80% 的 bug 是最近改动引入的，先查这里。
4. 环境变了什么：依赖升级了？配置改了？数据量变大了？

证据收集完，写三句话总结现状。写不出来，说明证据还不够，继续收集。

### 第三步：提假设

基于证据，列出 1 到 3 个最可能的根因，按可能性排序。写下来，不要只在脑子里过。

格式：

1. 最可能：XXX，因为证据 A 和 B 都指向它。
2. 次可能：YYY，如果 XXX 排除了，再看它。
3. 不太可能但要记住：ZZZ。

超过 3 个假设，说明证据不足，回去收集证据。假设太多等于没假设。

### 第四步：设计最小验证实验

每个假设，对应一个最小验证实验——一次只动一个变量：

- 加一行日志，看变量到底是什么值
- 写个最小测试，隔离出可疑代码单独跑
- 注释掉一段代码，看问题还在不在
- 换个小输入，看问题跟不跟输入规模走

先验证最可能的假设。验证的目的是排除，不是证明。对了就继续，错了就划掉，下一个。

### 第五步：二分定位

问题范围太大时，用二分法缩小：

- 注释掉一半代码，问题还在吗？在 → 问题在这一半；不在 → 在另一半。
- mock 掉一层依赖，问题还在吗？
- 每次实验只改一个变量。一次改两个地方，实验结果就作废了。

二分几次，范围就缩到一个函数、一行代码。这时候根因基本就露脸了。

### 第六步：说清楚根因，再写修复

找到根因后，先用一句话说清楚：

> "因为 X，所以 Y。"

说不清楚这句话，就还没找到真根因，继续挖。"好像是缓存的问题"不是根因，"缓存 key 没带用户 ID，导致 A 用户看到 B 用户的数据"才是。

根因说清楚了，再写修复。修复必须附带回归测试（走 tdd-red-green 的修 bug 流程：先写复现测试，红 → 修 → 绿）。

### 第七步：修完三件事

1. 复现步骤重跑一遍：确认好了。有验证证据，不许说"好像好了"。
2. 全量测试跑一遍：确认没修坏别处。
3. 举一反三：同类问题还有哪里？至少扫一遍相邻代码。缓存 key 没带用户 ID，别处还有没有类似的 key？

### 第八步：3 个假设全被证伪，停下来

如果连续 3 个假设都被证伪、还在原地打转，停下来：

1. 把已知证据、已排除的假设写下来。
2. 换视角：问人、看文档、去喝口水。闷头再试 2 小时，成功率极低。
3. 考虑升级：这是不是该找更熟悉这块代码的人看看？

停下来不是认输，是止损。侦探卡住了会回去重新看案卷，不会在现场瞎转。

## 示例

用户："导出 CSV 功能挂了，报 500 错误，帮我看看。"

AI（错误示范）："我看看……可能是内存问题，我把读取改成分页试试。" ——没复现、没看日志、直接改。改完可能好了，可能没好，反正不知道为什么。

AI（正确示范）：

AI："先复现。你点导出的时候，筛选条件是什么？数据量大概多少？"
用户："筛选了上个月的订单，大概 3 万条。"
AI："好，我在本地造 3 万条数据复现一下。……复现了，500 错误。看日志：`MemoryError`，报错在 `export.py:58`，`''.join(rows)` 这一行。最近改动：上周把流式写入改成了一次性拼接（git log 看到的）。
假设：一次性拼接 3 万行字符串内存爆炸。验证：加一行日志打印 `rows` 的长度和拼接前的内存占用。
……日志确认了，拼接时内存涨了 800 MB。根因：`''.join(rows)` 一次性在内存里拼 3 万行 CSV，大数据量下内存爆炸。
修复：改回流式写入，用 generator 逐行 yield。回归测试：写一个 5 万条数据的导出测试，断言内存占用低于阈值且文件行数正确。
修完：复现步骤重跑，3 万条导出成功；全量测试通过；扫了一遍，另一个导出 Excel 的地方也有一次性拼接，顺手改了。"

## 边界

- 没复现不许改业务逻辑，这是铁律。加日志、加监控、写最小复现脚本不算改业务逻辑，可以先上。
- 不许一次改多个地方"看看哪个管用"。一次一个变量，实验结果才有效。
- 修完不许说"好像好了""应该没问题了"。拿出验证证据：复现步骤的结果、测试结果。
- 生产环境出问题，先止血（回滚、降级、关开关），再按这个流程找根因。找根因和止血是两件事，别混在一起。
- 日志和监控不足导致无法定位时，修 bug 的第一步是补日志和监控，不是猜。
