## 这是什么

一句话：本技能包的总控——拿到开发任务时，先读我，再决定用哪几个 skill、按什么顺序用。

8 个 skill 如果同时触发，一个小改动也要过澄清的复述确认、计划的三句话，用户会觉得烦。总控的作用就是一件事：**按任务大小，拼出刚好的流程，不多不少**。

## 何时用

- 用户交给你一个开发任务（新功能、修 bug、重构），你不知道该按什么顺序干活时
- 几个 skill 的触发条件同时满足，你不知道先用哪个时
- 用户说"按你们那套方法论来"，指的就是这个

## 工作流

### 第一步：判断任务类型和大小

先把任务分成三档：

- **S（小）**：改动不超过 30 行，单文件，逻辑简单。例：改个文案、修个拼写、加个日志。
- **M（中）**：新功能、修 bug、跨 2–3 个文件。例：加个导出按钮、修个 500 错误。
- **L（大）**：新模块、多人协作、动核心链路。例：重写支付流程、上线新服务。

分错档比不分更糟。拿不准时，按大一档处理。

### 主动声明

M 档和 L 档任务，如果用户没明确要求跳过，**主动说一句**：

> "这个任务我按完整流程走：先澄清需求，再给你计划确认。"

不要默默走全流程（用户会觉得你怎么问这么多），也不要等用户问"你按什么流程"。S 档任务不用声明，直接干。

如果用户明确说"别问了，直接做"，不要硬走流程。声明一句：

> "好，我跳过澄清，直接按你的理解做，风险自负。"

然后按 S 档处理：直接干，但动手前把你的理解复述一遍（半句话就行），给用户最后一次纠正的机会。

### 压缩规则：不同项目类型

标准流程按任务大小拼，但项目类型不同，有些步骤可以压缩：

- **纯前端 UI 微调**（样式、文案、排版）：按 S 档走。TDD 可跳过（没有逻辑可测），但澄清不能省——"改成什么样"必须确认。
- **一次性脚本**（用完即扔的数据处理脚本）：跳过 TDD 和评审，保留复述确认。脚本超过 100 行，按 M 档走。
- **基础设施代码**（CI 配置、Dockerfile、部署脚本）：按 M 档走，计划和评审必须有；TDD 换成"改完跑一遍流水线验证"。
- **英文项目**：其他 8 个 skill 照常，`write-chinese-docs` 不触发（它只管中文文档）。
- **中英双语项目**：中文文档走 `write-chinese-docs`，英文文档保持原样，不混用。

### 第二步：按档位拼流程

**S 档流程**：直接干。只在写完后心里过一遍 review-five-axes 的五个维度（不用输出评审报告）。

- 跳过：clarify-first（需求已经清楚）、plan-before-code（三句话都不用）
- 保留：写完自查一次

**M 档流程**：澄清 → 计划 → TDD → 评审。

1. 需求有一点模糊？走 clarify-first。需求已经很清楚？跳过，但复述确认那一步不许省。
2. 走 plan-before-code：超过 30 行写完整计划，不超过写三句话。
3. 写代码走 tdd-red-green。
4. 写完走 review-five-axes，自己先评一遍再交。

**L 档流程**：澄清 → 计划 → TDD → 评审 → 复盘。

1. 必须走 clarify-first，完整 9 步。
2. 必须走 plan-before-code，完整计划，用户书面确认。
3. 拆成 M 档子任务，每个子任务走 TDD。
4. 每个子任务走 review-five-axes。
5. 做完走 retrospective，输出复盘。

**修 bug 专用流程**：debug-like-detective → tdd-red-green（修 bug 专用流程）→ review-five-axes。

- 需求澄清通常可跳过（bug 本身就是需求），但复现步骤要写下来。
- 计划可压缩成三句话：根因是什么、怎么修、怎么验。

**重构专用流程**：refactor-small-steps 全程。

- 重构前需求一般是清楚的，clarify-first 可跳过。
- 计划就是重构清单（第二步），不用另写。

### 第三步：skill 之间交接

上一个 skill 的输出，是下一个 skill 的输入，交接时带上：

- clarify-first → plan-before-code：把"澄清结果留痕"那 5–10 行直接贴进计划开头。
- plan-before-code → tdd-red-green：计划里的"验证方法"就是第一个测试的断言来源。
- tdd-red-green → review-five-axes：告诉评审"我是按 TDD 写的，测试在 XX 文件"，评审重点看测试没覆盖到的地方。
- 任何一步 → retrospective：过程中记下的"坑"和"下次注意"，直接进复盘的事实部分。

### 第四步：用户说"跳过"时

用户明确说"别问了，直接做""不用计划"，照做，但要留痕：

1. 把你要跳过的步骤用一句话发出来（"好，那我跳过计划，直接写代码"）。
2. 风险自负：跳过的步骤，默认你承担了返工成本。出问题别抱怨流程，是你自己点的跳过。

用户没说跳过，你不许自作主张跳过。觉得流程烦，先走完，事后用 retrospective 提改进。

## 示例

用户："登录页面的按钮错位了，修一下。"

AI（总控判断）：单文件样式问题，S 档。直接修，修完心里过一遍五个维度：正确性（按钮能点吗）、边界（小屏幕呢）、可读性、安全、性能。没问题，交。

用户："给订单系统加个优惠券叠加功能。"

AI（总控判断）：跨多文件、动核心链路，L 档。全流程：先 clarify（优惠券能和满减叠加吗？上限呢？）→ 完整计划用户确认 → 拆子任务 TDD → 每个子任务评审 → 上线后复盘。跟用户说："这个我按完整流程走，先对一下需求。"

## 边界

- 总控只负责排流程，不代替具体 skill。排完流程，每个 skill 的铁律照样生效。
- 档位是建议，不是枷锁。用户要求走完整流程，哪怕 S 档任务也照走。
- 紧急线上故障：总控让位。先止血（回滚、降级），流程事后补。
- 不许为了"显得专业"把 S 档任务包装成 L 档。流程是成本，不是勋章。
