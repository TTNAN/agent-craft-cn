## 这是什么

一句话：按"事实 → 归因 → 可执行的行动项"做复盘，下次不踩同一个坑。

复盘有两种烂法。一种是表扬稿："在大家的共同努力下，项目取得了圆满成功"——等于没复。另一种是甩锅稿："都是测试没测出来"——下次继续踩坑。

这个 skill 规定：先摆事实（不许带评价），再挖根因（挖到系统/流程层，不许停在"人的失误"），最后输出行动项（每条有负责人、有截止时间、有验收标准）。少一条，这个复盘就是走过场。

## 何时用

- 项目上线后（成了也要复：是实力还是运气？下次能复制吗？）
- 线上故障处理完，48 小时内
- 迭代结束，固定节奏复盘
- 搞砸了一件事之后——越不想复，越要复

## 工作流

### 第一步：摆事实，不带评价

只写发生了什么，不写"应该""本可以"。拉一条时间线：

- 几点几分发生了什么
- 谁做了什么操作
- 影响多大：用数字——故障时长、受影响用户数、回滚次数、损失金额

事实部分不许出现评价词。"响应很慢"不行，"P99 从 200 ms 涨到 8 s"行。"测试不充分"不行，"回归测试覆盖了 12 个用例，漏掉了支付回调这个分支"行。

数字拿不出来？先去拉数字。没有数字的复盘，归因就是拍脑袋。

### 第二步：挖根因，至少挖到系统层

用"五个为什么"往下挖，至少挖到系统/流程层：

- 表层：小王把配置写错了。
- 为什么写错能上线？→ 因为配置变更不需要 review。
- 为什么不需要 review？→ 因为配置一直是手动改的，没进版本控制。
- 根因：配置变更没有版本控制和 review 流程。

"因为小王粗心"不是根因。停在"人的失误"，就是甩锅。人都会犯错，系统要能接住人的失误。

归因禁区（出现就重写）：

- 不许出现人名作为根因。"小王粗心"不行，"缺少 code review 环节"行。
- 不许用"加强重视""提高意识"当结论。这是空话，不是行动项。重视不能当饭吃，流程才能。

### 第三步：写行动项，四个要素缺一不可

每条行动项必须同时满足：

1. **具体动作**：做什么。"把配置纳入版本控制"，不是"加强配置管理"。
2. **负责人**：一个名字。不是"大家"、不是"团队"。没名字就没有主人，没有主人就没人做。
3. **截止时间**：年月日。"下周完成"不行，"10 月 20 日前"行。
4. **验收标准**：怎么算完成。"配置变更走 PR + review 流程跑通一次"行。

缺一个要素，就不算行动项，打回去重写。

**负责人和截止时间必须问用户**：不许编人名、不许编日期。编出来的行动项等于没写，宁可空着等用户填。

### 第四步：行动项不超过 5 条

超过 5 条等于没有重点。排个优先级，砍到 5 条以内。剩下的进 backlog，别扔。

砍的标准：哪个不做，下次还会踩坑？按这个排序。

### 第五步：一页纸

复盘文档控制在 1 页纸：

- 事实：1/3 篇幅
- 归因：1/3 篇幅
- 行动项：1/3 篇幅

写长了没人看。没人看的复盘，等于没复盘。

### 第六步：行动项进跟踪

下次复盘，第一件事：检查上次的行动项完成了几个。

没完成的，说明原因，重新定时间。不许无声无息烂掉。烂掉两次的行动项，说明它本身有问题（太大、没资源、不现实），拆小或砍掉，诚实面对。

## 示例

用户："昨天线上出故障了，帮我写个复盘。"

AI（错误示范）："## 复盘：10-11 订单故障\n\n在大家的共同努力下，故障于 2 小时内恢复。反思：测试同学要加强重视，开发同学要提高意识。以后大家多注意。" ——表扬稿 + 空话 + 甩锅，三宗罪全占。

AI（正确示范）：

AI："先对一下事实，你确认：

**事实**：
- 10-11 14:02，订单服务 P99 从 200 ms 涨到 8 s，持续 47 分钟。
- 14:05 收到报警，14:12 定位到是新上线的优惠券叠加逻辑，14:49 回滚恢复。
- 影响：约 3200 笔订单超时，用户投诉 41 起。
- 当天 13:30 上线了优惠券叠加功能，未灰度，直接全量。

对吗？有没有要补充的数字？"

用户："对，差不多。"

AI："好，归因。连问几个为什么：

1. 为什么优惠券逻辑会拖慢所有订单？→ 叠加计算里有个循环查库，N+1，没走缓存。
2. 为什么 N+1 能上线？→ code review 时没人看出来，review 只看了 10 分钟。
3. 为什么没灰度？→ 发布流程里灰度是可选的，赶时间就跳过了。

根因：发布流程中灰度环节可选 + review 走过场。不是'小王写了 N+1'，是流程允许 N+1 上线。

**行动项**：
1. 灰度发布改为强制环节，跳过需要 TL 审批 —— 负责人：（问用户，不许编）—— 截止时间：（问用户，不许编）—— 验收：下一次发布走完灰度流程。
2. 给订单核心链路加压测基线，N+1 类问题在压测阶段暴露 —— 负责人：（问用户，不许编）—— 截止时间：（问用户，不许编）—— 验收：压测报告里包含 P99 对比。
3. review checklist 加上'循环里有没有查库' —— 负责人：（问用户，不许编）—— 截止时间：（问用户，不许编）—— 验收：checklist 文档更新并同步团队。

三条，够了。文档我按一页纸整理好，你确认后归档。下次复盘我们先检查这三条。"

## 边界

- 复盘不对人，只对事。点名只出现在"负责人"栏，不出现在"归因"栏。归因里出现人名，重写。
- 成功项目也要复盘：是实力还是运气？运气好不复盘，下次运气不好就翻车。能复制的才叫方法论。
- 不许为了"正能量"美化事实。故障 47 分钟就是 47 分钟，不写成"短时间内迅速恢复"。美化事实的复盘，归因一定是错的。
- 故障复盘 48 小时内完成。拖久了细节全忘光，复盘就变成编故事。
- 复盘会上不许打断、不许辩解。先听完事实，再讨论归因。开场就辩解的人，下次没人敢说真话。
