## 这是什么

一句话：结构化的代码评审框架，五个维度逐项过，只报真问题。

AI 做代码评审有两种烂法。一种是"看起来不错，没什么问题"——等于没评。另一种更糟：为了显得认真，硬挑刺，"建议把 `i` 改成 `index`"、"这里可以加个空行"。这种评审浪费所有人的时间，还败人品。

这个 skill 规定：评审按正确性、边界条件、可读性、安全、性能五个维度走。每个报出来的问题，必须回答"不改会怎样"。答不上来，就不报。

## 何时用

- 用户说"帮我 review 这段代码"
- 提 PR 之前，自己先自查一遍
- AI 自己写完代码后，换位当评审再看一遍
- 接手别人的代码，先评审再动手改

## 工作流

### 第一步：读全 diff，再开口

没读全就别评论。只看了一个函数就下结论的评审，和算命没区别。先把改动涉及的文件、调用链、前后文看完。

### 第二步：五个维度逐项检查

每个维度有检查清单，一项一项过：

**1. 正确性：逻辑对吗？**
- 条件分支覆盖全了吗？if-else 有没有漏掉的情况？
- 循环的起止条件对吗？差一错误（off-by-one）是最常见的。
- 能举出一个反例让这段代码出错吗？举不出来才算过。

**2. 边界条件：极端情况想过吗？**
拿这张表逐项过，至少在心里过一遍：
- 空值 / None / null
- 空数组、空字符串、空字典
- 0、负数、超大数字
- 超大输入（10 万条数据进来会怎样？）
- 并发（两个请求同时到，会打架吗？）
- 超时和重试（下游挂了，这里会卡死吗？）

**3. 可读性：半年后的人能看懂吗？**
- 函数名说谎吗？（名叫 `get_user`，实际还发了封邮件？）
- 魔法数字有名字吗？（`if x > 3` 的 3 是什么？）
- 嵌套超过 3 层吗？超过就该抽函数了。
- 注释解释的是"为什么"，而不是"是什么"吗？

**4. 安全：有没有洞？**
- 用户输入进 SQL、进 shell 命令、进 HTML 了吗？（注入三件套）
- 密钥、token 进日志了吗？
- 越权了吗？（用户 A 能看到用户 B 的数据吗？）
- 敏感操作有二次确认或鉴权吗？

**5. 性能：数据量大了会炸吗？**
- 循环里查数据库了吗？（N+1 问题）
- 大数据量下内存扛得住吗？
- 有没有明显可以省掉的重复计算？
- 小项目这项可以简写，但不能跳过思考。写一句"数据量小，暂无性能问题"也行，证明你想过。

### 第三步：只报真问题

每个候选问题，过一遍这个过滤器：

> "这个问题不改，会出 bug、难维护、还是有安全风险？"

答不上来，不报。评审的目标是让代码变好，不是让你显得认真。

### 第四步：标注严重级别

每个问题必须带 severity：

- **blocker**：必须改。不改会出故障、丢数据、有安全漏洞。
- **major**：应该改。有实质风险，但不至于立刻爆炸。
- **minor**：建议改。可改可不改，纯属更好。

minor 超过 3 条，就是凑数。砍掉，只留最值得说的。评审意见贵精不贵多。

### 第五步：每个问题的固定格式

```
[blocker] src/cart.py:42
现象：空购物车结算时抛未捕获异常。
为什么是问题：用户清空购物车后点结算，500 错误。
怎么改：结算前检查 `cart.is_empty()`，抛业务异常 `EmptyCartError`，前端给友好提示。
```

位置、现象、原因、改法，四项缺一不可。只说"这里有问题"不给改法的评审，等于没说。

### 第六步：总体结论

最后给一句话结论，三选一：

- **通过**：没 blocker，可以合。
- **小改后通过**：有 major，改完不用再评。
- **打回重写**：有 blocker，或 major 多到说明设计有问题。

结论后面跟一句话理由。不要写"总体来说写得不错，提了几点小建议"这种和稀泥的话。

## 示例

用户："帮我 review 这段代码。"（贴了一段用户注册的代码）

AI（错误示范）："代码整体写得不错，逻辑清晰。几点小建议：1. 变量名 `u` 可以改成 `user` 更清晰；2. 这里可以加个空行；3. 建议补充注释……" ——全是凑数的 minor，真问题一个没看到。

AI（正确示范）：

AI："读完了。结论：**打回重写**，有一个 blocker。

[blocker] `register.py:28`
现象：密码直接拼进 SQL 字符串。
为什么是问题：SQL 注入。用户名填 `admin' --` 就能绕过，整个用户表随便看。
怎么改：用参数化查询。`cursor.execute("INSERT ... VALUES (%s, %s)", (username, pwd_hash))`。另外密码必须存哈希，不能存明文。

[major] `register.py:35`
现象：注册成功没有校验邮箱格式。
为什么是问题：`aaa` 这种也能注册，后续发邮件全失败，还污染用户表。
怎么改：正则校验邮箱格式，不合法直接 400。

别的没了。命名、空行这种我不评，那是 formatter 的事。"

## 边界

- 不评审风格偏好：括号换行、单引号双引号这种，扔给 formatter，不许在评审里报。
- 不重写整个实现：只指出问题、给改法方向。不替他把代码重写一遍——那是结对编程，不是评审。
- 一次评审只看当前 diff：不翻旧账。"这个文件三年前就写得烂"不是本次评审的内容。
- 用户明确说"只看安全"时，其他维度闭嘴。评审范围用户说了算。
- 被评审的是 AI 自己写的代码时，更要狠。自己评自己，最容易手软。
