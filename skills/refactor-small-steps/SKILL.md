## 这是什么

一句话：重构要小步快跑，每一步都能验证、都能回滚。

一听到"这代码太烂了，重写吧"，老工程师心里都会咯噔一下。大爆炸重写有三个结局：写到一半烂尾；写完了发现丢了一堆边界 case；新代码三个月后和旧代码一样烂，只是烂法不同。

这个 skill 规定：重构一次只做一步。每步改完，测试全绿，能单独提交，能一句话说清楚。步子小，错了也亏得起。

小步重构和大爆炸重写，区别不在改动大小，在有没有保护网：小步重构每一步都有测试护航，随时能停、随时能回滚；大爆炸重写一次性推倒，几周内没有可工作的版本，风险全押在最后。除非技术栈整体换代、原代码没人能看懂且没测试、业务逻辑本身要推倒重来，否则不选重写。即使重写，也用绞杀者模式：新旧并存，逐个替换，而不是一次性切换。

## 何时用

- 代码有坏味道，但能跑：函数太长、重复代码、命名说谎
- 加新功能之前，先把地基整一整（否则新代码盖在烂地基上）
- 测试护得住，想还技术债
- 读不懂一段代码，重构是读懂它的最好方式

## 工作流

### 第一步：动手前先过三问

不是所有烂代码都值得重构。动手前问三个问题：

1. 这块代码未来三个月还要改吗？不改，就别动。能跑的烂代码，比被重构坏的好代码强。
2. 测试护得住吗？护不住，先补测试，或者别动。
3. 现在是合适的时机吗？上线前夜、大促前一周，烂代码也给我忍着。

三个都通过，才动手。重构是投资，不是洁癖发作。

### 第二步：确认有测试护航

没有测试，不许重构。这是铁律。

先检查要动的代码有没有测试覆盖。没有？先补测试（走 tdd-red-green，给关键路径补上）。无测试重构，等于高空走钢丝不系绳——掉下来只是时间问题。

要动的函数没有测试在调用它，先补测试再重构，不许硬上。

### 第三步：列清单，按风险排序

把想改的地方列出来，按"风险从小到大"排序：

1. 最安全的先：改名、抽常量、删注释掉的死代码、格式化
2. 中等：抽函数、合并重复代码、简化条件表达式
3. 最后：拆类、改接口、动数据结构

先易后难。简单的改完，测试全绿，你对这块代码的理解也深了，难的才敢下手。

### 第四步：一次只做一步

"一步"的定义，三个条件同时满足：

- 改完能跑全量测试
- 能单独提交（`git commit` 一次，diff 一目了然）
- 能一句话说清楚改了什么

举例：把 `calculate()` 拆成 `calculate_subtotal()` 和 `calculate_tax()`，这是一步。拆完顺手把旁边的 `format()` 也重写了，这是两步，不许混在一起。

### 第五步：每步说明"改了什么、为什么安全"

每做完一步，写两句话：

> 改了什么：把 200 行的 `process_order` 拆成 4 个小函数。
> 为什么安全：纯拆分，没改任何逻辑；全量测试 48 个全绿；有类型检查兜底。

"为什么安全"必须具体。"我觉得没问题"不算理由。测试全绿算，纯改名无行为变化算，编译器/类型检查通过算。

### 第六步：红灯停

每步改完，跑全量测试。红了？

1. 回滚这一步（`git stash` 或 `git checkout`）。
2. 想清楚为什么红，再来。
3. 不许"带着红灯继续走"。红灯下继续改，你都不知道新红的是哪一步引入的。

### 第七步：重构中不加功能、不修 bug

一次只做一件事。重构时发现 bug？记下来，重构完再修。重构时想加个功能？记下来，重构完再加。

混在一起的后果：出了问题，你分不清是重构引入的，还是新功能引入的。排查时间翻倍。

### 第八步：收尾检查

全部步骤做完：

1. diff 自己读一遍，确认没有计划外的行为变化。
2. 跑一遍完整验证（测试 + 关键流程手动点一点）。
3. 更新相关文档（README、注释里提到旧结构的地方）。



### 第九步：照手法速查表从低风险做起

按风险从低到高排列，照着这个顺序做，基本不会翻车：

| 手法 | 干什么 | 为什么安全 |
|---|---|---|
| 改名 | 变量、函数名改成说人话的 | 纯改名，IDE 自动重构，行为零变化 |
| 抽常量 | 魔法数字、魔法字符串给名字 | 同上，行为零变化 |
| 删死代码 | 删掉注释掉的旧代码、没人调的函数 | git 里有历史，删错了能找回来 |
| 抽函数 | 把一段逻辑抽成独立函数 | 配合测试，行为不变 |
| 合并重复 | 两处一样的逻辑合成一处 | 测试覆盖两处，合完都绿就行 |
| 简化条件 | 卫语句代替嵌套 if、提取布尔变量 | 逻辑等价变形，测试验证 |
| 拆大函数 | 300 行函数拆成几个小函数 | 一次拆一个，每步跑测试 |
| 拆类/改接口 | 动结构 | 风险最高，放最后，调用方逐个改 |

## 示例

用户："这个 `process_order` 函数 300 行，看着头疼，重构一下。"

AI（错误示范）："好，我重写一个 `OrderProcessor` 类，设计更优雅……" ——三天后，新类有了，旧函数的边界 case 丢了三个，测试挂了五个。

AI（正确示范）：

AI："先看测试覆盖。`process_order` 有 12 个测试，覆盖主要路径，可以动。重构清单（按风险排序）：
1. 把魔法数字抽成常量（零风险）
2. 把校验逻辑抽成 `validate_order()`（低风险）
3. 把价格计算抽成 `calculate_total()`（中风险）
4. 把通知逻辑抽成 `send_notifications()`（中风险）
一次做一步，每步跑测试。开始第 1 步。"

（第 1 步做完）
AI："第 1 步完成。改了什么：把 `0.13`、`86400` 等 5 个魔法数字抽成命名常量。为什么安全：纯改名，行为零变化；12 个测试全绿。提交。继续第 2 步？"

用户："继续。"
AI："……第 4 步完成。收尾：diff 读了一遍，无计划外行为变化；全量测试通过。`process_order` 从 300 行降到 60 行，4 个新函数各有单一职责。过程中发现一个 bug（优惠券叠加时税率算错了），记下来了，没在这次动，你要修的话我们另起一轮。"

## 边界

- 重构不许改变外部行为。除非用户明确要求，否则输入输出必须和以前一模一样。
- 测试护不住时，先补测试，不许硬上重构。
- "重写"需要用户明确批准。默认只做小步重构。你说"重写吧"，用户说"好"，才能重写。
- 工期紧急时，重构让位给交付。把想重构的地方记下来（TODO + 原因），以后再做。不许在上线前夜重构核心流程。
- 重构不是炫技：不要为了"优雅"引入团队没人懂的设计模式。半年后维护的人能看懂，比"优雅"重要十倍。
