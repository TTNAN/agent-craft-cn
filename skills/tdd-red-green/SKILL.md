## 这是什么

一句话：测试先行，红 → 绿 → 重构，三步循环。

先写实现、后补测试，是自欺欺人。后补的测试永远在"证明我的代码是对的"，而不是"发现我的代码是错的"。覆盖率 90%，该挂还是挂。

这个 skill 规定的顺序是死的：先写一个失败的测试（红），再写最少的代码让它通过（绿），最后重构。顺序反了，这个 skill 就白装了。

## 何时用

- 写新功能、新函数、新模块
- 修 bug：先写能复现 bug 的测试，再修
- 重构前：先给要动的代码补测试，当保护网
- 不适用：探索性 spike（先探路，路探明了再补测试）、纯 UI 排版微调、一次性脚本（用完就扔的那种）

## 工作流

### 红：写一个失败的测试

1. 只写一个测试，描述一个行为。一次只干一件事。
2. 测试命名规范：`test_<场景>_<期望>`。看到名字就知道在测什么。
   - 好：`test_空购物车_结算时抛异常`
   - 烂：`test_checkout_1`
3. 运行它，确认它是红的（失败）。注意：如果一上来就是绿的，你的测试写错了——它什么都没验证。回去重写。
4. 红的确认方法：故意让它失败是不够的，要确认失败的原因是你预期的那个原因。报错信息看一眼，别红得莫名其妙。

### 绿：写最少的代码让它通过

1. 目标只有一个：让测试变绿。允许写"笨"代码，允许硬编码，允许 if-else 堆。
   - 测试说"空购物车结算抛异常"，你就写 `if cart.is_empty(): raise`。别想着"优雅"，先绿。
2. 不过多设计：测试没要求的，一行都别写。YAGNI（你不会需要它）是这里的铁律。
3. 变绿后，运行全部测试，确认没有把别的测红。绿了这个、红了那个，等于没绿。

### 重构：现在才轮到代码洁癖

1. 测试全绿的前提下，重构：去重、改名、抽函数、删硬编码。
2. 每改一步，跑一次测试。必须保持绿色。红了就回滚这一步，想清楚再来。
3. 重构只动内部结构，不改变行为。行为变了，那叫加功能，回去走"红"。

### 循环：下一个行为

一个行为走完红-绿-重构，再开始下一个行为。不要一次写五个测试再一起实现——步子大了，红了你都不知道是哪个红的。

### 修 bug 专用流程

1. 先写能复现 bug 的测试，确认它是红的（复现成功）。
2. 修代码，让测试变绿。
3. 这个测试不许删。它是回归保护，下次同样 bug 冒头，它第一个报警。
4. 想一想：同类 bug 还有哪里？至少扫一遍相邻代码。

### 测试质量自查

写完测试，问自己三个问题：

1. 这个测试失败时，我能一眼看出是哪里坏了吗？（断言信息清楚吗？）
2. 这个测试依赖外部状态吗？（读真实数据库、调真实接口、依赖当前时间——都要干掉，用注入、mock、固定时钟。）
3. 测试里有 `sleep` 吗？有就重写。`sleep(2)` 是 flaky 测试的万恶之源。



### 测试替身：什么时候用什么

测试要快、要稳，外部依赖必须替掉。用错替身，测试就变成摆设：

| 替身 | 干什么 | 什么时候用 |
|---|---|---|
| 固定值 | 写死的时间、随机种子 | 依赖"当前时间""随机数"的逻辑 |
| Fake | 能跑的轻量实现（内存数据库） | 需要数据库，但不想起真实数据库 |
| Mock | 断言"被调用了几次、参数是什么" | 验证有没有发邮件、有没有调接口 |
| Stub | 返回预设数据，不验证调用 | 下游接口还没好，先造数据顶着 |

原则：能用真东西就用真东西（真实的排序、真实的计算），只有慢、不稳定、不可控的东西才替掉。满屏 mock 的测试，测的是 mock，不是代码。

### 测试文件放哪里

- 和源码放一起：`cart.py` 配 `test_cart.py`，同目录。找起来快，删代码时不会漏删测试。
- 测试之间不许有顺序依赖：每个测试独立 setup/teardown，单独跑、乱序跑、并行跑，结果都一样。
- 一个测试只断言一件事。断言了五件事的测试，挂了你都不知道挂的是哪件。



### 顶住借口："先写实现，写完一起补测试"

- "我先写实现，写完一起补测试，效果一样。" ——不一样。后补的测试只会证明代码是对的，发现不了 bug。你敢不敢先写测试，让测试先失败一次？不敢，就说明你在怕。
- "这个太简单了，不用测。" ——简单的才要测，写测试 2 分钟，线上翻车 2 小时。真简单，测试写起来也简单。
- "UI 怎么测？" ——测 UI 背后的逻辑，不测像素。按钮点下去调了哪个函数、传了什么参数，这些都能测。纯排版微调可以不测，写清楚为什么不测。
- "项目赶时间，来不及。" ——赶时间更要写测试。返工的时间，永远比写测试的时间长。你现在省 10 分钟，上线后花 2 小时修 bug，还要被用户骂。

## 示例

用户："给购物车加个满 100 包邮的逻辑。"

AI（错误示范）：直接写实现，写完补个测试"证明"满 100 包邮是对的。边界呢？正好 100 呢？优惠券叠加呢？全没测。

AI（正确示范）：

AI："先写测试。"

```python
def test_满100包邮_正好100元时免运费():
    cart = Cart([Item(price=100)])
    assert cart.shipping_fee() == 0

def test_满100包邮_99元时收运费():
    cart = Cart([Item(price=99)])
    assert cart.shipping_fee() == 10
```

AI："跑一下，两个都是红的（`shipping_fee` 还不存在）。好，开始写最简实现："

```python
def shipping_fee(self):
    return 0 if self.total() >= 100 else 10
```

AI："绿了，全量测试没红。现在重构：把 100 和 10 抽成常量 `FREE_SHIPPING_THRESHOLD`。改完再跑一遍，全绿。下一个行为：优惠券叠加怎么算？"

## 边界

- 不追求 100% 覆盖率凑数：覆盖率是副产品，不是目标。为凑数写的测试，本身就是垃圾代码。
- 不给 private 方法写测试：测行为，不测实现。实现变了测试就得改的测试，是负债。
- 测试里不许 `sleep` 等待：用依赖注入、mock、固定时钟。flaky 的测试不如没有。
- 同一个红灯连续 3 次都没变绿：停下来。不是测试的问题，是设计有问题。回去画个草图，想清楚再写。
- 探索性 spike 例外：先快速探路验证思路，路走通了，把 spike 扔掉，用 TDD 重写一遍。spike 代码不许直接进主分支。
